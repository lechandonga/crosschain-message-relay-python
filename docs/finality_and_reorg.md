# 最终性与回滚规则

## 确认与最终性

- 区块通过 `parent_hash` 哈希链接；消息进入某一高度的区块。
- 确认数 `confirmations(h) = head_height - h + 1`（含该区块本身）。
- 仅当 `confirmations(source_height) >= finality_depth`（默认 3）才允许投递。
- 未达最终性返回 `not_finalized`（可重试），**不会**投递，也不会推进 nonce。

## 重组（reorg）语义

`POST /reorg {"chain","depth"}` 用一条全新分叉替换链尾 `depth` 个区块，
并立即触发 `relayer.reconcile()`。状态由确定性规则重建，结果可复现：

1. **源链包含被回滚**：记录 -> `source_reorged`（终态），不再允许投递
   （再投递得到 `reorg_rollback`）。终态说明与资金归宿在重复对账下保持
   字节级稳定。
   - 若该消息**尚未在目标侧形成有效投递**（从未投递，或目标投递也已被
     回滚）：消息已不可再投递，源侧托管锁必须有确定归宿——
     - 重组本身先退还的锁，保持“已退款”；
     - 投递成功后保留的 `settled` 锁因目标兑付消失而成为孤儿锁，
       由对账恰好退还一次给发送方（`release_unbacked_send`），不无限悬空。
     - `note` 写明 `refunded <amount> to <sender> ... not redeliverable`，
       并保留 `delivered_height` 等回滚历史；先目标回滚后源回滚、先源回滚
       后目标回滚两种顺序收敛到**同一终态、同一资金归宿**。
   - 若该消息**已在目标侧生效且投递仍规范**：投递效果保留，发送方**不会**
     再得到退款——同一消息在两条链上合计只保留一次资金效果。具体地：投递
     成功时源侧托管锁即被标记为 `settled`，重组遇到已 settled 的发送会
     **保留**托管金而不是退款；若重组发生在投递确认之前的狭窄窗口（退款已
     先发生），`reconcile()` 会把这笔退款**追回**回托管（note 中标注
     `compensated`，该补偿历史持久保留）。无论哪种时序，对账后两侧账面合计
     都与重组前一致。
   - 记录保留 `delivered_height`，历史不被抹除或覆盖。
2. **源仍规范，但目标投递被回滚**：记录 -> `target_reorged`。
   - 目标侧资金已从接收方恢复到 `escrow`；源侧 `settled` 锁暂时保留，因为
     消息仍可重投、兑付可能再次成立。
   - 消息重新可投递；再次 `relay_once` 恰好生效一次，之后重复提交得到
     `duplicate_delivery`。
   - 若**此后源包含也被回滚**，立即按第 1 条收敛为 `source_reorged`，
     孤儿托管锁退还发送方。
3. **源与目标都规范**：维持 `delivered`，幂等。
4. **`failed`/`expired` 终态之后源链再重组**：状态、note 与已完成的退款均
   不变。永久失败与过期只影响当下这条消息，其结论不被后续重组覆盖，也与
   暂时性故障明确区分。

### 退避重试与重组交错

一条消息在退避等待、尚未投递成功时，源侧先完成重组与对账：

- 等待中的那次尝试在**下一次投递提交前**（提交段线程锁内）重新核对源包含
  与记录终态，发现已为 `source_reorged` 后立即以 `reorg_rollback` 中止；
- 目标侧**不会**因此产生新的入账，已确定的重组结论**不会**被“投递成功”
  覆盖；
- 最终记录稳定保留重组终态、资金说明与“不可再次投递”结论；再次对账返回
  空 `affected`，再次投递仍是 `reorg_rollback`。

## 永久失败与过期的资金归宿

单条消息的永久失败只影响它自己：

- `target_rejected`（目标永久拒绝）与 `retries_exhausted`（重试打满）都会
  进入 `failed` 终态，`note` 以对应原因开头，可彼此区分，也可与暂时性故障
  （`attempts` 里的 `transient_failure`/`timeout`）和超时区分。
- 终态时仍锁在源侧 `escrow` 的资金**恰好退款一次**给发送方
  （`note` 中写明 `refunded <amount> to <sender>`）；资金不会无限期悬空。
  过期（`expired`）消息同理退款。
- 失败消息的 nonce 被视为**已消费**：通道游标立即越过它，同通道后续消息
  照常投递；重组后游标重建同样把 `failed`/`expired` 计入已消费。
- 已被源重组移除的消息（`source_reorged`）**不**消费 nonce：该序号可被
  重新提交使用。

### 确定性与可复现

- 重组深度相同、重组前状态相同，则对账后状态、note、游标完全一致。
- 重复执行 `reconcile()` 不再产生变化（幂等）：不移动资金、不改记录或说明；
  首次对账实际发生的退款/追回动作，在 note 中体现为稳定的**最终归宿**
  描述而非“本次是否移动资金”，因此第二次对账的 note 与第一次完全一致。
- 通道 nonce 游标在每次对账后从记录确定性重算：
  `游标 = 1 + 最大的“从最小值起连续已消费”nonce`，其中已消费 =
  已规范投递、已永久失败或已过期；`source_reorged` 不消费 nonce。

### 深度边界

- 重组深度必须为正且不超过当前链高（genesis 高度 0 不可回滚），否则
  链层抛出 `ValueError`。
- 只有被移除区块中“记录在区块内容里”的投递会回滚；更早深度的投递不受影响
  （浅重组保留更早投递）。

## 并发一致性

- 每个消息 id 持有独立 asyncio 锁：不同消息可并发，同一消息严格串行。
- 每个消息 id 另有一把只覆盖“资金 + 记录/游标提交段”的 **threading 锁**：
  同步的 `reconcile()` 与 `/reorg` 端点运行在独立线程，可能在一次退避 sleep
  期间执行；提交段锁保证它们不会与投递的资金/记录提交交错（退避等待本身
  不持锁，不被对账阻塞）。
- 多个处理者竞争同一消息，最终状态与某个合理串行执行一致：恰好 1 次
  `delivered`（或确定的重组终态），其余为 `duplicate_delivery`/
  `reorg_rollback`，余额只变动一次，审计中只有一条成功 attempt。
- 投递、重试、目标回滚、源侧对账以任意顺序交错，同一消息只产生一次资金
  效果，无“只完成一半”的记录状态；资金归宿由两侧规范链事实唯一决定
  （见 architecture.md 的收敛表），重复重算无额外影响。
- nonce 游标推进与记录置为 `delivered` 在同一消息提交段内完成，外部永远
  观察不到“已投递但游标未推进”之类的半更新状态。

## 积压与限流

- 待处理队列容量固定为 `queue_capacity`（默认 256），满则 `submit` 抛
  `backpressure`，内存不会无界增长。
- worker 数量固定为 `max_inflight`（默认 8），即并发上限。
- 同一已排队 id 的重复提交被合并（返回 False 而非重复入队）。
- 被背压拒绝的消息稍后重试即可，投递仍保证恰好一次。
