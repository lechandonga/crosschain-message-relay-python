# 最终性与回滚规则

## 确认与最终性

- 区块通过 `parent_hash` 哈希链接；消息进入某一高度的区块。
- 确认数 `confirmations(h) = head_height - h + 1`（含该区块本身）。
- 仅当 `confirmations(source_height) >= finality_depth`（默认 3）才允许投递。
- 未达最终性返回 `not_finalized`（可重试），**不会**投递，也不会推进 nonce。

## 重组（reorg）语义

`POST /reorg {"chain","depth"}` 用一条全新分叉替换链尾 `depth` 个区块，
并立即触发 `relayer.reconcile()`。状态由确定性规则重建，结果可复现：

1. **源链包含被回滚**：记录 -> `source_reorged`（终态），不再允许投递。
   - 若该消息**尚未投递**：源侧 `escrow` 退还给原发送方（恰好一次），
     源链总量守恒。
   - 若该消息**已在目标侧生效**：投递效果保留，发送方**不会**再得到退款——
     同一消息在两条链上合计只保留一次资金效果。具体地：投递成功时源侧
     托管锁即被标记为 `settled`，重组遇到已 settled 的发送会**保留**托管金
     而不是退款；若重组发生在投递确认之前的狭窄窗口（退款已先发生），
     `reconcile()` 会把这笔退款**追回**回托管（note 中标注
     `compensated`）。无论哪种时序，对账后两侧账面合计都与重组前一致。
   - 若**目标投递也已不存在**（目标先回滚、源随后也回滚，或相反顺序）：
     托管锁不再有任何投递背书，`reconcile()` 把它**恰好释放一次**退回
     发送方（note 写明 `refunded <amount> to <sender>`），资金不会无限期
     悬空在托管账户里。
   - 记录保留 `delivered_height` 与全部 `attempts`（回滚历史不抹除），
     `note` 明确写出资金去向（`escrow lock retained` / `compensated` /
     `refunded ...` / `funds refunded`）；再次投递得到 `reorg_rollback`。
2. **源仍规范，但目标投递被回滚**：记录 -> `target_reorged`。
   - 目标侧资金已从接收方恢复到 `escrow`。
   - 消息重新可投递；再次 `relay_once` 恰好生效一次，之后重复提交得到
     `duplicate_delivery`。
3. **源与目标都规范**：维持 `delivered`，幂等。

## 永久失败与过期的资金归宿

单条消息的永久失败只影响它自己：

- `target_rejected`（目标永久拒绝）与 `retries_exhausted`（重试打满）都会
  进入 `failed` 终态，`note` 以对应原因开头，可彼此区分，也可与暂时性故障
  （`attempts` 里的 `transient_failure`/`timeout`）和超时区分。
- 终态时仍锁在源侧 `escrow` 的资金**恰好退款一次**给发送方
  （`note` 中写明 `refunded <amount> to <sender>`）；资金不会无限期悬空。
  过期（`expired`）消息同理退款。
- 失败消息的 nonce 被视为**已消费**：通道游标立即越过它，同通道后续消息
  照常投递；重组后游标重建同样把 `failed`/`expired` 计入已消费。
- 已被源重组移除的消息（`source_reorged`）**不**消费 nonce：该序号可被
  重新提交使用。

### 确定性与可复现

- 重组深度相同、重组前状态相同，则对账后状态、note、游标完全一致。
- 重复执行 `reconcile()` 不再产生变化（幂等）：不移动资金、不改记录。
- 通道 nonce 游标在每次对账后从记录确定性重算：
  `游标 = 1 + 最大的“从最小值起连续已消费”nonce`，其中已消费 =
  已规范投递、已永久失败或已过期。

### 深度边界

- 重组深度必须为正且不超过当前链高（genesis 高度 0 不可回滚），否则
  链层抛出 `ValueError`。
- 只有被移除区块中“记录在区块内容里”的投递会回滚；更早深度的投递不受影响
  （浅重组保留更早投递）。

## 并发一致性

- 每个消息 id 持有独立 asyncio 锁：不同消息可并发，同一消息严格串行。
- 多个处理者竞争同一消息，最终状态与串行执行一致：恰好 1 次
  `delivered`，其余为 `duplicate_delivery`，余额只变动一次，审计中只有
  一条成功 attempt。
- nonce 游标推进与记录置为 `delivered` 在同一消息锁内完成，外部永远观察
  不到“已投递但游标未推进”之类的半更新状态。

## 交错时序的收敛规则

投递、重试、目标回滚与源侧对账可以任意交错；以下规则保证结果等价于
某个合理的串行执行：

- **重试退避中源侧重组并已对账**：退避等待发生在“对账保护段”之外，
  因此 `reconcile()` 可以先把记录定为 `source_reorged` 终态。等待中的
  那次尝试醒来后会在**投递前重新校验**（终态 + 源侧规范性），随后以
  `reorg_rollback` 拒绝——目标侧不会产生新的入账，已确定的重组终态、
  说明与“不可再次投递”的结论也不会被覆盖成成功投递；再次
  `reconcile()` 返回空、记录与账面都不再变化。
- **已投递后目标回滚、源包含也被重组移除**（任意先后顺序）：目标侧已
  不存在有效投递，源侧那笔失去背书的托管锁由 `reconcile()` 恰好释放
  一次退回发送方；记录保留 `delivered_height` 回滚历史并在 `note` 中
  写明 `refunded <amount> to <sender>`，资金不会无限期悬空。
- **串行化手段**：除每消息 asyncio 锁外，中继还有一把“对账保护锁”
  （线程可重入）。每次投递尝试的 [投递前重校验 + 目标入账 + 记录/游标/
  托管结算] 与整个 `reconcile()` 都在该锁内完成，因此即使对账从
  HTTP 线程池与事件循环并发触发，二者也只会一前一后执行；永久失败与
  过期的终态结算同样不会覆盖已确定的 `source_reorged` 结论。
- **单次资金效果**：同一消息在任意交错下只产生一次资金效果（要么目标
  入账、要么发送方退款，二者只居其一）；重复执行状态重算
  （`reconcile()`）不移动资金、不改记录。

## 积压与限流

- 待处理队列容量固定为 `queue_capacity`（默认 256），满则 `submit` 抛
  `backpressure`，内存不会无界增长。
- worker 数量固定为 `max_inflight`（默认 8），即并发上限。
- 同一已排队 id 的重复提交被合并（返回 False 而非重复入队）。
- 被背压拒绝的消息稍后重试即可，投递仍保证恰好一次。
